## Executive summary

The project is a camera-guided two-axis water turret intended primarily to keep
pigeons off a balcony. The repository already had a substantial server, web UI,
installer, simulator, calibration/targeting system, and ESP32 firmware. This
chat concentrated on making the current generic YOLO detector observable and
measurable before changing models or building more elaborate inference logic.

The main result is an evidence-first detection workflow:

- The current CPU-only YOLO path remains the default.
- New installations default to a 960-pixel inference input and `bird` class.
- Low-confidence proposals can be saved without entering tracking or targeting.
- Original camera frames and model metadata are persisted for review.
- A Detections page supports review, manual missed-detection capture, rejection,
  retention, and marking useful examples for future training.
- Detection events are now written to the event log.
- Stale/frozen camera results no longer remain actionable.
- The model's own class vocabulary is exposed to the settings UI.
- AI and target class fields now use model-aware autocomplete/chips and flag
  unknown or internally incompatible names.
- A replacement model is loaded before the working model is closed. If loading
  fails, the previous detector continues running and the error is surfaced.

The work is already committed and present on `origin/main` in three commits:

## Product intent and decisions made in the chat

These decisions should be treated as current direction unless real-world test
data justifies changing them.

### Hardware and control

- There is no assembled turret yet. The immediate priority is working software;
  physical construction comes afterward.
- The planned mechanism contains a camera and water nozzle in the turret.
- ESP32 GPIO/pin mapping is deliberately deferred until the actual hardware is
  being assembled.
- Combined homing is acceptable. The ESP32 should own the homing procedure; the
  web UI does not need more detailed homing sequencing.
- No physical emergency-stop button is planned. The existing software e-stop
  can remain.
- Existing motion, valve, arming, watchdog, homing, limit, and spray guards were
  not removed. The user considers the consequence relatively low because the
  output is water, but retaining these controls is useful and inexpensive.

### Detection objective

- Species-level classification is unnecessary.
- The operative class is the generic model class `bird`.
- Almost all birds on the balcony are expected to be pigeons; occasional crows
  or other birds may also be targeted as `bird`.
- The exact COCO label is singular: `bird`, not `birds`.
- `person` may be enabled alongside `bird` for observation/testing.
- Detection classes and target classes have intentionally separate meanings:
  the detector may observe both `bird` and `person`, while targeting can remain
  restricted to `bird`.

### Compute and model strategy

- Keep GPU use optional and unnecessary for the normal service. Available GPUs
  are intended for other workloads and should not need to run continuously for
  this project.
- CPU-only YOLO at roughly 6 inference frames per second is acceptable.
- A pigeon normally remains present for seconds or minutes, so sub-second
  reaction is not required.
- Increase inference input size because the camera covers a wide view and birds
  will be small. The new-install default is 960 pixels.
- Do not add motion-gated inference yet.
- Do not add a larger second-stage confirmation model yet.
- First collect evidence from real pigeons and determine whether misses or false
  positives are actually a problem.

### Evidence and future training

- Save low-confidence proposals so the system's behavior can be measured.
- Preserve uncertain examples rather than only saving confident successes.
- Allow manual saving of a frame when a visible bird was missed.
- Review results in the web UI and retain potentially useful examples.
- The current work prepares a dataset but does not train or export a model yet.

### AI approaches considered and why they were deferred or selected

The discussion did not assume that the existing model was the final answer. We
considered several inference designs and deliberately chose the simplest one
that can produce real balcony evidence first.

#### Current generic object detector: selected as the baseline

The current `yolov8n.pt` is a small generic COCO object detector. It returns
bounding boxes, confidences, class IDs, and names, which is exactly the shape of
output needed by the existing tracker and aiming pipeline.

Reasons to keep it for the first real test:

- It already runs acceptably on CPU at the configured rate.
- It detected and tracked a person well in the actual camera view.
- COCO includes the generic `bird` class, which matches the product requirement.
- Species identification would add complexity without improving the intended
  behavior: any bird may be discouraged from the balcony.
- It requires no training data before field testing can begin.
- A detector, unlike an image-level classifier, provides the location needed
  for tracking and aiming.

Known uncertainty:

- A small generic model may miss distant or small pigeons in the wide camera
  view.
- Its generic `bird` training distribution may not match infrared/grayscale,
  balcony geometry, unusual poses, or partial occlusion.
- Successful person detection is evidence that the pipeline works, not proof of
  adequate bird recall.

The selected response was to raise the inference input from 640 to 960 pixels
for new installations and collect real examples before replacing the model.

#### Larger or newer generic detector: possible later comparison

A larger generic detector could improve small-object recall or reduce unstable
class guesses, but it would also increase CPU time, RAM use, and possibly
latency. Choosing one from public benchmarks alone would not establish that it
performs better on this specific balcony and camera.

If the evidence gallery shows repeatable misses, the useful comparison is to
run candidate models against the same retained balcony frames and compare:

- bird recall at relevant distances;
- false bird detections on the empty balcony;
- box stability across adjacent frames;
- CPU inference time and sustainable FPS;
- memory use;
- model load/replacement behavior.

No specific larger model was selected in this chat.

#### Two-stage detector/classifier cascade: plausible, but not yet needed

One proposed design was:

1. Run a small detector continuously at about 6 FPS and a low proposal
   threshold.
2. When it sees something uncertain or bird-like, submit a crop or source frame
   to a larger model.
3. Use the second result to confirm whether tracking/targeting should proceed.

This is plausible because pigeons usually land and remain for many seconds. A
one- or two-second confirmation delay would be acceptable.

Potential advantages:

- The expensive model would run only for candidate episodes.
- A crop classifier could reject some low-confidence false bird proposals.
- The fast detector could continue to provide location while confirmation is
  pending.

Costs and unresolved design questions:

- More model lifecycle, queueing, timeout, and state-machine complexity.
- A second model may still consume substantial resident memory even when idle.
- Loading it on demand avoids idle memory but creates long cold-start latency.
- False first-stage triggers could still wake the expensive model frequently.
- A classifier confirms crop identity but does not correct a poor bounding box.
- Confidence scores from different models are not automatically comparable.

Decision: defer the cascade until real captures show that the small detector
produces useful candidates but cannot confidently separate birds from recurring
false positives.

#### Motion/change-gated inference: attractive for power saving, but deferred

Another proposed design was to detect image changes or motion cheaply and run
YOLO only when the scene changes.

Potential advantages:

- Lower average CPU use on an empty, mostly static balcony.
- Less continuous inference work and possibly lower power consumption.

Risks and complications:

- Exposure changes, infrared illumination, rain, moving plants, shadows, camera
  noise, and compression artifacts can trigger motion constantly.
- A pigeon can land during a missed change event and then sit still.
- Once a target becomes stationary, a pure motion gate stops supplying fresh
  detections and can break tracking/verification.
- Camera reconnects and automatic gain changes need special handling.
- A robust implementation would still need periodic unconditional inference as
  a heartbeat, plus hysteresis and carefully selected regions of interest.

Decision: continuous CPU inference at 6 FPS is currently acceptable and much
simpler. Consider motion gating only if measured CPU/power use becomes a real
problem. If implemented, it should be an optimization around periodic YOLO, not
the only way detections are initiated.

#### GPU inference: optional capability, not a service requirement

The server has GPUs, but the user wants them available for other workloads and
does not want the electricity cost or operational coupling of running them for
the turret continuously.

Decision:

- Keep `cpu` as the normal/default device.
- Do not make CUDA, a GPU container, or GPU scheduling part of the required
  deployment.
- Retain the existing optional CUDA setting for experiments or offline
  evaluation.
- Prefer spending available CPU/RAM on a slightly larger input or model only if
  field evidence shows a benefit.

#### Custom fine-tuned detector: valuable only after enough representative data

A custom model may eventually be the best way to improve recall for small
pigeons and reduce balcony-specific false positives. It is premature without a
representative dataset.

The evidence workflow was therefore implemented first. A useful training set
would need:

- positive pigeon/bird frames at different distances, poses, times, and weather;
- empty-balcony and confusing-object negatives;
- corrected bounding boxes, including boxes for manually saved misses;
- duplicate control so adjacent frames do not dominate the dataset;
- train/validation/test separation by episode or day, not random adjacent
  frames;
- evaluation on held-out balcony footage.

Decision: do not train merely because images are available. First determine
whether the generic detector actually fails in a consistent way, then add
annotation/export and fine-tuning as a measured response.

#### Classification-only and classical motion detection: not replacements

- An image-level classifier can answer whether a bird exists but cannot provide
  the bounding box needed to aim. It could only be a second-stage component.
- Classical background subtraction or motion blobs can locate change but cannot
  reliably distinguish a bird from a person, shadow, plant, or lighting change.
  It may be a compute gate, not the targeting model.
- Segmentation was not considered necessary because bounding boxes are already
  adequate for the current tracking/aim-point design.

#### Agreed decision rule

Do not change AI architecture based on hypothetical superiority. Use the saved
evidence to identify the actual failure mode, measure candidates on the same
frames, and adopt the least complex approach that fixes the demonstrated
problem.

## Current architecture

The existing repository remains the source of truth. The high-level design is:

```text
RTSP/ONVIF or simulated camera
        |
        v
latest-frame buffer (drop old frames)
        |
        +---------------------> browser preview
        |
        v
VisionPipeline at configured FPS
        |
        +--> YOLO raw proposals
        |       |
        |       +--> low capture threshold --> evidence/event subscriber
        |       |
        |       +--> operational threshold --> ByteTrack
        |                                      |
        |                                      v
        |                                target selection
        |                                      |
        |                                calibration/zones
        |                                      |
        |                                targeting state machine
        v                                      |
SQLite metadata + JPEG evidence                v
                                         TurretManager
                                               |
                                     WebSocket protocol
                                               |
                                      ESP32 or simulator
```

### Server

- Python/FastAPI, running as one process and one Uvicorn worker because model,
  cameras, and controller connections are in-memory singleton resources.
- `Runtime` in `server/app/services/runtime.py` constructs and coordinates all
  subsystems.
- Blocking camera decode, JPEG encoding, and inference work is moved away from
  the asyncio event loop.
- REST is used for settings and one-shot actions.
- Browser and hardware WebSockets carry telemetry/control connections.
- MJPEG and snapshots provide camera imagery.

### Vision and targeting

- `CameraManager` owns named camera sources; only the selected primary camera
  enters detection, calibration, zones, and automatic targeting.
- `VisionPipeline` always consumes the newest frame and never accumulates an
  inference backlog.
- `YoloDetector` wraps Ultralytics YOLO.
- `ByteTracker` supplies stable identities.
- `TargetSelector` applies class, confidence, track age, zone, mapping, and
  selection-policy rules.
- The targeting state machine controls detection stability, aiming,
  verification, spray, result checking, retries, and cooldown.
- `TurretManager` is the only motion/control path for both simulated and
  physical modes.

### Persistence

- SQLite stores settings, calibration points, zones, presets, events, and
  detection-capture metadata.
- Camera credentials remain in their protected external credentials file and
  are not exposed by the API.
- Runtime data defaults below the deployment data directory.
- Detection JPEGs default to the `detections` subdirectory and can be moved with
  `TURRET_DETECTION_DIR`.
- Schema migration version 2 introduces the detection-capture table. Existing
  databases receive the new table through the project's `create_all` migration
  strategy without overwriting user data.

### Web UI

- React + TypeScript + Vite + Tailwind.
- Important pages include Dashboard, Cameras, Calibration, Zones, Detections,
  Settings, Events, and System.
- The new Detections page renders bounding boxes as an overlay on the stored raw
  frame. Boxes are not burned into the saved JPEG.

### Firmware

- ESP-IDF/PlatformIO firmware owns trajectories, homing, endstops, valve timing,
  watchdog behavior, and hardware-side limits.
- The server sends angles and intents rather than step pulses.
- The mechanics have not been commissioned and final pin mapping is deferred.
- VS Code appears to show two firmware folders, but there is only one physical
  `firmware/` directory. `pigeon-tracker.code-workspace` lists the repository
  root and then lists the same `firmware/` path again under the display name
  `firmware (PlatformIO)` so PlatformIO sees `platformio.ini` at a workspace
  root. Editing either Explorer entry edits the same files.

## Work completed in detail

### 1. Repository inspection and context reconstruction

The repository, documentation, Git history, settings schema, server runtime,
vision path, UI, tests, installer, and firmware structure were reviewed before
making changes. No old chat context was assumed; code and Git history were used
as the source of truth.

The main architecture was already coherent: a single server runtime owns camera
sources, vision, tracking, mapping, targeting, controller state, telemetry, and
persistence. The simulator uses the production command path, which remains the
right way to test before mechanics exist.

### 2. Frozen/stale vision-result handling

The previous pipeline could retain its last result after a camera stopped
producing frames. That could leave stale detections/tracks in telemetry and make
downstream targeting appear active even though the image was no longer fresh.

The pipeline now:

- Rejects results from a camera that is no longer the configured primary.
- Rejects results when the primary source is disconnected.
- Rejects results older than the camera's stall timeout.
- Clears tracker state when results are invalidated.
- Invalidates results on camera changes, detector failures, and disabled
  detection.
- Exposes `result_stale` in vision status.
- Clears the runtime's last selection instead of retaining an old target in
  telemetry.

This is specifically about stale actionable vision state. A browser may still
show the last decoded camera image while a source reconnects, depending on the
preview path, but that frame is no longer used as a live target.

Tests are in `server/tests/test_vision_pipeline.py`.

### 3. Detection event logging

The user observed successful visual person detection but no detection entries
in the event log after running the service for a day. Vision results had not
been connected to persistent class-presence events.

`Runtime` now subscribes to `VisionPipeline` results and emits detection events
containing:

- camera ID;
- class name;
- count of that class in the frame;
- maximum confidence;
- frame sequence;
- linked capture ID when evidence was saved.

The event input is the low-confidence capture proposal list when evidence
capture is enabled; otherwise it is the operational detection list. Events are
collapsed by camera and class using the configured re-arm interval, so the same
continuously visible object does not create an event every inference tick.

Tests are in `server/tests/test_detection_events.py`.

### 4. Separate evidence and operational confidence tiers

One confidence threshold could not serve both purposes:

- Tracking/targeting needs a reasonably conservative threshold.
- Evidence collection should retain uncertain model proposals.

The detector now exposes two filters:

- `capturable(...)` uses `capture_confidence` when evidence capture is enabled.
- `operational(...)` uses the normal `confidence` threshold.

Only operational detections enter tracking. Low-confidence evidence proposals
cannot become targets merely because they were saved.

Ultralytics inference uses the lower relevant threshold so those proposals are
not discarded inside the model before application filtering.

Tests are in `server/tests/test_detector.py`.

### 5. Detection evidence storage

`DetectionCaptureStore` was added in
`server/app/services/detection_capture.py`.

Each automatic capture stores:

- the original full-resolution source frame as JPEG;
- timestamp and camera ID;
- automatic/manual trigger type;
- primary class and confidence;
- frame sequence and dimensions;
- configured model name;
- every proposal and bounding box retained for that frame;
- a snapshot of detector settings;
- review status and review label.

Images receive sanitized, unique filenames. Database insertion failure removes
the newly written JPEG. Image lookup rejects path traversal.

Automatic capture behavior is class-presence based:

- Presence is tracked separately per camera and case-insensitive class name.
- A continuously present class produces one capture/event.
- It becomes eligible again after being absent longer than
  `capture_rearm_s`.
- When several classes become due in one frame, one image is stored with all
  proposals; separate class events may link to that same capture.

This is episode/re-arm deduplication, not perceptual-image deduplication. A weak
static false positive that flickers in and out can therefore create repeated
captures.

### 6. Detection review UI and API

The Detections page provides:

- filtering by review state and class;
- lazy-loaded raw images;
- proposal bounding-box overlays;
- timestamp, camera, trigger, model, and confidence metadata;
- **Confirm bird**, which marks the record `training` with label `bird`;
- **Not a bird**, which marks it `rejected` with label `not-bird`;
- reset to `unreviewed`;
- permanent deletion;
- **Save current frame** for a visible object the model missed.

API endpoints:

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/api/detection-captures` | List/filter captures with pagination |
| `POST` | `/api/detection-captures/manual` | Save current primary frame |
| `PATCH` | `/api/detection-captures/{id}` | Update review status/label |
| `DELETE` | `/api/detection-captures/{id}` | Delete metadata and JPEG |
| `GET` | `/api/detection-captures/{id}/image` | Return protected JPEG |

All are covered by the normal API authentication guard.

Review states are `unreviewed`, `training`, and `rejected`.

Important dataset limitation: confirming an automatic capture retains its
existing model boxes, which may be approximate or wrong. A manual missed-object
capture has no boxes. There is not yet a box editor, dataset exporter, or model
training pipeline, so reviewed images are useful source material rather than a
ready-to-train dataset.

### 7. Detection evidence retention

New retention settings:

- `detection_retention_days`: default 90 days;
- `max_detection_mb`: default 2048 MB.

Maintenance removes old unreviewed/rejected captures and then removes the
oldest unreviewed/rejected images until the storage budget is met. Captures
marked `training` are protected.

Protected training captures can intentionally cause actual usage to exceed the
configured budget if enough are retained. This should be monitored once real
data collection begins.

### 8. CPU and input-size defaults

New installations now default to:

| Setting | Default |
| --- | ---: |
| Device | `cpu` |
| Model | `yolov8n.pt` |
| Model classes | `bird` |
| Inference input | 960 px |
| Inference rate | 6 FPS |
| Operational confidence | 0.35 |
| Evidence capture | enabled |
| Capture confidence | 0.10 |
| Capture re-arm | 5 seconds |
| Capture JPEG quality | 90 |
| Target classes | `bird` |
| Target minimum confidence | 0.50 |

Persisted settings are not overwritten during an update. An existing install
that previously saved `auto` and 640 pixels will keep those values. Change them
explicitly in Settings if CPU/960 is desired.

The previous README benchmark of roughly 73 ms per frame was measured at 640
pixels on two CPU cores. The 960-pixel path has not been formally benchmarked
in this chat and should be measured on the actual server.

### 9. Class-field comma bug

The original controlled text field parsed its value into a list after every
keystroke. Typing `bird,` immediately converted back to `bird`, making it
impossible to enter the next class.

Commit `fe37cd7` introduced an intermediate input fix. Commit `a875f87` then
replaced the plain comma field with the final model-aware class picker described
below.

### 10. Model class catalog and autocomplete

Ultralytics models expose their vocabulary through the model's `names` map.
The backend already read this data but `DetectorStatus.as_dict()` did not
serialize it, so the UI could not use it.

The loaded model's class names are now exposed. An authenticated endpoint was
added:

```text
GET /api/detector/catalog
```

It reports:

- active and configured backend/model;
- whether the current vocabulary corresponds to the configured model;
- loading and replacement-error state;
- available model classes;
- configured detector and target classes;
- invalid detector names;
- invalid target names;
- target classes excluded by the detector filter.

The Settings UI now provides:

- browser-native autocomplete from the active model vocabulary;
- removable selected-class chips;
- case-insensitive canonicalization to the model's spelling;
- explicit **All model classes** in AI settings;
- explicit **All detected classes** in targeting settings;
- red chips/warnings for classes absent from the loaded model;
- red chips/warnings for target classes excluded by the AI class filter;
- target suggestions constrained by the detector filter;
- model status, class count, loading state, and replacement error.

Unknown entries are deliberately preserved and flagged rather than silently
deleted. This matters during a model change and prevents an invalid list from
accidentally becoming an empty list, because an empty list means “all classes.”

### 11. Atomic model replacement

Previously, the active detector was closed before replacement weights were
loaded. A bad path or incompatible model left detection unavailable.

The pipeline now:

1. Takes a copy of the desired detector settings.
2. Creates and loads a candidate detector in a worker thread.
3. Keeps the current working detector resident and unclosed during loading.
4. Discards the candidate if settings changed again while it loaded.
5. Swaps only after successful loading.
6. Keeps the previous detector if replacement fails.
7. Exposes the failure and marks AI health degraded until corrected.

Candidate loading runs in a worker thread, so it does not block FastAPI's event
loop. The vision pipeline awaits that load, however, so inference pauses during
the replacement attempt. If loading fails, subsequent inference resumes with
the preserved old detector.

The configured model value remains the user's requested value after a failed
replacement. The UI shows that the old model is still active; the operator must
correct or revert the configured model.

Model changes do not modify configured class lists. Once the replacement loads,
the existing names are revalidated against its vocabulary. Shared names keep
working. Unknown names remain visible but match nothing. If every configured AI
class is invalid, the model still runs but the application accepts no
detections until the filter is corrected.

Tests cover failed replacement preservation and successful atomic swap in
`server/tests/test_vision_pipeline.py`.

## Exact class semantics

This distinction caused several questions and is important for continuing work.

### AI → Classes

This is the detector acceptance filter used for evidence, operational
detections, and tracking.

- Empty / **All model classes** means accept every class the model produces.
- `bird` means accept only birds.
- `bird, person` means observe, log, capture, and track both.
- Names are compared case-insensitively but must otherwise match the model.
- For `yolov8n.pt`, `bird` and `person` are valid; `birds` is invalid.

### Targeting → Target classes

This is the subset of tracked classes eligible for automatic targeting.

- Empty / **All detected classes** means every tracked class can be targeted.
- `bird` means people may be detected/tracked but only birds are targetable.
- `bird, person` makes both classes targetable.
- A target class excluded by AI → Classes can never receive a track and is now
  flagged in red.

For the intended real system, the recommended configuration is generally:

```text
AI classes:       bird
Target classes:   bird
```

Temporarily using `bird, person` for AI classes is useful to verify the camera
and model. Keep Target classes at `bird` unless intentionally testing person
target selection in simulated/no-water mode.

## Real observations from the running installation

The user deployed the evidence UI and observed:

- Person detection worked well and produced a moving box with confidence around
  the high-0.8/0.9 range.
- With AI Classes empty and capture confidence at 0.10, roughly 40 evidence
  images appeared in only a few minutes.
- The static balcony scene produced weak, flickering COCO labels such as book,
  TV, chair, dining table, suitcase, and handbag.
- This behavior was expected: empty means all model classes, and the intentionally
  low evidence threshold retains uncertain proposals.

The correct response is to configure the intended class set rather than raise
the evidence threshold immediately. With `bird` selected, only bird proposals
will create evidence. Some low-confidence false “bird” captures are still
expected and are useful for measuring model behavior.

No real pigeon results were available during this chat. Bird recall, small-bird
box quality, CPU load at 960 pixels, and practical false-positive rate remain
unmeasured.

## What was deliberately not implemented

- Motion/change gating before YOLO inference.
- A larger second-stage confirmation model.
- GPU inference as a requirement.
- Pigeon-vs-crow or species classification.
- Custom model training.
- Dataset export in YOLO/COCO format.
- Bounding-box editing/annotation.
- Perceptual duplicate detection or scene clustering.
- Automated accuracy metrics such as precision/recall.
- Notifications based on detections.
- Physical turret GPIO mapping.
- More granular homing control in the web UI.
- A physical emergency-stop input.

These are candidates only after evidence from actual pigeons shows a concrete
need.

## Known limitations and cautions

1. **Real bird performance is unknown.** Person success does not guarantee
   sufficient recall on small birds in the wide view.
2. **Capture threshold is intentionally noisy.** At 0.10, weak false positives
   are expected.
3. **Re-arm is not image deduplication.** Flickering static false positives can
   repeatedly reappear after the absence interval.
4. **Manual captures have no annotation.** They need a future box editor or
   external labeling tool before supervised detector training.
5. **“Confirm bird” is a coarse review label.** It does not verify or correct
   every stored box.
6. **Training records are retention-protected.** They can make the detection
   directory exceed its nominal budget.
7. **Unknown class names are warnings, not save blockers.** An all-invalid AI
   filter yields zero accepted detections by design.
8. **Changing model paths can trigger an Ultralytics download.** The old model
   stays active while a candidate loads, but peak RAM may temporarily include
   both models.
9. **Current README test count is stale.** It still mentions 180 tests in some
   places; the current suite contains 194 tests.
10. **Frontend build was not rerun on the temporary Windows PC.** Standalone
    Node/npm was unavailable there. TypeScript/TSX syntax was parsed with VS
    Code's bundled TypeScript, and the deployed Detections UI was exercised by
    the user. Run the full npm build on the main PC.
11. **One test warning remains.** FastAPI's test client reports a Starlette
    deprecation warning about `httpx`; it does not fail the suite.

## Deployment and operational notes

- The install/update script is designed to preserve settings, calibration,
  zones, events, credentials, models, and runtime data.
- Existing deployments should be updated through the documented installer
  management flow rather than replacing `/var/lib/turret-control`.
- Pre-update backups are retained by the installer.
- After updating, check **Settings → AI** because old saved values override new
  defaults.
- For the intended test, explicitly set:

```text
Device:              cpu
Input size:          960
AI classes:          bird
Capture enabled:     yes
Capture confidence:  0.10
Operational conf.:   0.35
Inference rate:      6 FPS
Target classes:      bird
```

- Check the model status panel for `model loaded`, the active model name, and
  available class count.
- Review the Detections page periodically rather than allowing unreviewed data
  to accumulate indefinitely.
- Application images and SQLite data are runtime artifacts and are not stored
  in Git.
